01 / CONCEPTS

领域语言

aic 的词汇表是规范性的（CONTEXT.md 定义）——代码、文档、提交消息都用同一套词。理解这 8 个词，就理解了整个工具。

▶
Run

默认提交工作流的一次执行：要么对已 stage 的文件做一次提交，要么对未 stage 的工作做一次批次规划。

▣
Batch

LLM 拆分计划分配给一次提交的一组文件/hunk。一个 Run 包含一个或多个 Batch；每个 Batch 产出一条提交。

✎
Drafted Message

LLM 为一个 Batch 的 diff 起草的 Conventional Commit 消息（含可选 body）。

⇄
Batch staging

把 Batch 计划的 hunk 映射到当前 index→workdir diff 并 stage 的阶段——重读新 diff 而非计划时快照，所以 pre-commit hook 不会让后续 Batch 失步。

▦
Block

确定性分组引擎（无 LLM）产出的原子变更单元，携带 BlockHeuristic（为什么这些 hunk 被合并）。一个 Block 转换为一个 Batch。

⏣
Backend

aic 获取 LLM 回答的方式——恰好两种：API-provider（HTTP 调 Provider）或 CLI-agent（shell 出外部 CLI 复用其认证）。由 backend_kind 显式判别。

⚡
Conflict / Resolution

Conflict = 检测到的合并态冲突；Resolution = LLM 产出的无标记文件内容。批准后写入工作树并 stage。

✓
Finalize

结束 Conflict 的 git 操作（git commit / cherry-pick --continue / revert --continue），用 git 默认消息，不调 LLM。

03 / MAIN FLOW

主流程：一次 Run

入口 default_workflow() 装配真实依赖 → default_run() 先检查冲突态（有冲突则提供 resolve 移交）→ 干净仓库进入 commit_run()，按「是否有已 stage 文件」二分为两条路径。

路由 git.status() → staged 文件集

决策
status = git.status()?
if staged_files.is_empty() && unstaged.is_empty() → “nothing to commit”，结束（不调 LLM）
if staged_files.is_empty()               → 路径 B：批次规划（unstaged）
else                                    → 路径 A：单次提交（staged）

路径 A — 有已 stage 文件 一次提交

1
折入工作树变更git.add(paths)
git add 语义：把 staged 文件的 workdir 改动折进 index。纯删除文件跳过（路径守卫：add(&[]) 会退化为 add -A，绝不允许）。
2
抓取 staged diff → JSON 信封git.diff → diff_json::files_json
逐文件从 index 读 live diff，scope 化格式化（按函数分块标注），组装成 {"files":[{path,diff}]}。
3
起草消息Generator::generate_commit_message → CommitOutput{message,body}
单次类型化调用：schema 约束 + 容错解析 + 重试，全部藏在 LLMAgent seam 里。进度条是纯 spinner（消息路径不流式）。
可选：confirm_before_commit
4
确认菜单workflow/confirm
Commit / Re-generate（重跑 LLM）/ Edit（$EDITOR 编辑）/ Abort。Re-generate 与 Edit 回到同一菜单。
5
提交 + 渲染 ✓ 行git.commit → display.commit_line
真 git commit CLI（hooks/gpgsign 生效），返回 hash；落地统计（committed_stats）渲染 File stats footer。

路径 B — 无 staged、有 unstaged hunk 级批次规划 —— aic 的灵魂

1
快照 workdir diff（每文件一次）git.diff_workdir → parse_file_patch
同一份快照喂两个必须对齐 hunk 编号的消费者：发给模型的编号视图 + file_hunk_counts（校验用）。零文本 hunk 的文件（二进制/权限/重命名）发送显式 BINARY_MARKER，防止模型当作“没变化”丢掉。
2
LLM 批次规划（流式）Generator::split_patch_streaming → BatchPlanOutput
模型边思考边把推理流进 Reasoning feed（原位滚动重绘，思考结束即擦除）。产出 {batches:[{changes:[{file,hunks:[1,3]}], reason}]} —— 一个文件的不同 hunk 可以分属不同批次（git add -p 式）。
3
校验：精确 hunk 划分generator::validate_batch_plan
每个文件的每个 hunk 必须恰好分给一个批次：无重叠、无遗漏、无越界、无未知文件。无效 = LLM 故障而非用户问题 → 警告并降级到确定性分组（见 §07），Run 继续完成。
ADR 0014：并发上限 8
4
并发起草全部批次消息buffered × MAX_CONCURRENT_DRAFTS = 8
计划的全部 diff 内容在计划时已知 → N 个串行 LLM 往返折叠为一次。每条草稿挂自己的 [i/N] 进度条；保序 buffered 让调用顺序确定。切片自计划时 diff（模型看到的编号），而非 staged diff。
5
逐批：stage → commit 循环staging::Staging::stage_batch → generate_and_commit
每批：把计划 hunk 重映射到当前 diff 并 git apply --cached（§05）→ 确认菜单 → 提交 → ✓ 行。中途失败/拒绝 = 干净中止，报「已提交 N 批，剩余仍 staged，重跑 aic 即可继续」。
为什么先全部起草再逐批提交？

LLM 往返主导多批 Run 的墙钟时间。计划一旦定下，每批的 diff 内容完全已知，fan-out 把 N 次串行等待坍缩成一次——而 staging 必须串行（每批提交改变 index，后续批次的当前 diff 会变）。上限 8 是防 provider 限流（HTTP 429）的护栏。

04 / TRUST BOUNDARY

计划校验：不信 LLM 一个字

LLM 输出是不可信输入。validate_batch_plan 把「批次计划」当作必须证明的命题：它是全部 hunk 的精确划分，否则整个计划作废，确定性引擎接管。

display.rs 的 5 个 hunk： h1h2h3h3…重叠 ✗h5h4 缺失 ✗
上图示意一个会被拒绝的计划：h3 被分给两个批次（重叠）、h4 没人认领（缺口）。合法计划 = 每个 hunk 恰好一种颜色，无空色、无重复。
校验规则拒绝原因（错误消息原文）
至少一个批次LLM returned no batches — no commits were created
批次非空batch N has no changes
不引用未知文件batch N references unknown file: …
hunk 索引在范围内batch N references hunk 5 of a.rs, which has only 2 hunk(s)
无重叠（一 hunk 一批次）hunk 2 of a.rs is assigned to more than one batch
无缺口（全覆盖）LLM response did not cover all hunks. Missing: a.rs:hunk 2…
零 hunk 文件（二进制）也必须被引用LLM response did not include every file. Unreferenced: blob.bin
回归防线

最后一条规则是真实回归的补丁：hunk 覆盖检查抓不到没有 hunk 的文件（二进制/权限/重命名）被遗漏——Run 会报成功却把变更留在工作树。同理，issue #34 的「静默零提交」由确定性分组的构造保证堵死：引擎输出必是合法划分，真实工作永远产出 ≥1 批。

05 / STAGING

Batch staging：两套索引空间的重映射

计划时模型看到的是「workdir vs HEAD」编号的 hunk；staging 时真正要 apply 的是「index vs workdir」的当前 diff——每批提交后 diff 都会变。Staging 状态机弥合这两套编号。

重映射算术
// Staging 内部：file → 已落地的【原始】hunk 索引集合
committed_hunks: HashMap<String, HashSet<usize>>

// 每批 stage 时：
1. 重读当前 diff（不是计划快照！）→ 当前 hunk 列表
2. 当前 hunk 中，减去已 committed_hunks 的，剩下 = 计划索引的直接映射
3. git apply --cached 选中 hunk → 落地索引记回 committed_hunks
4. 文件全部 hunk 已落地 → 该文件跳过（附提示），批次继续
为什么「重读当前 diff」是承重墙

lint-staged / prettier 类 pre-commit hook 会 re-stage 整个文件：第一个碰该文件的批次可能把它的全部 hunk 带进提交。如果重放计划时快照，后续批次的 git apply 会死在 "patch does not apply"。重读当前 diff 让后续批次看到「该文件已无剩余 hunk」→ 优雅跳过，Run 存活。历史 bug：3+ hunk 单文件 Run 因把重映射位置误写回原始索引而中止——所以状态只存原始索引。

06 / BACKENDS

LLM 双后端

取 LLM 回答的方式恰好两种，Backend 枚举分发（刻意不用 trait object——保持 schema<T> / 流式调用的泛型单态化）。backend_kind（"api"|"cli"）是唯一权威判别，休眠后端的配置字段保留但运行时忽略（ADR 0011）。

Backend::Rig — API-provider
  • 12 个 Provider 经 rig-core：OpenAI、Anthropic、Gemini、DeepSeek、Groq、Ollama、xAI、Mistral、OpenRouter、Perplexity、Together、OpenAI-compatible
  • REGISTRY 单一事实源（ADR 0003）：加 provider = 一行注册表 + 一个 default_model 臂 + 一个 with_agent! 臂
  • 类型化输出：schema::<T>（schemars 生成 JSON Schema）+ 容错 JSON 解析（截断/围栏容忍）
  • 流式 + 推理：stream_typed_with_reasoning 边解码 NDJSON 边把 thinking delta 喂给渲染层
  • 认证靠 api_key；Base URL 可覆写（OpenAI-compatible 必填，服务 LM Studio / vLLM / 网关）
Backend::Cli — CLI-agent（ADR 0010）
  • 无头 shell 出外部编码 agent：11 个预设（claude、codex、pi、opencode、omp、gemini 等）的 print 模式
  • 零 API key：复用该 CLI 自己的登录态/订阅
  • 配置是 command/args/timeout_secs 模板；NDJSON 流事件解码进共享 decoder
  • CommandRunner trait seam 是全库唯一 async-trait——为了测试注入 FakeRunner 队列
  • 不产出流式推理的 agent（冷启动）→ Reasoning feed 显示加载帧 + 过宽限期后的解释性提示

共享重试 llm/retry — 推理模型的「预算饥饿」

推理模型（如 DeepSeek）偶发把整个输出预算花在 reasoning_content 上，返回空 content 或截断 JSON。rig 把它们报成 EmptyResponse / DeserializationError——此前单次不走运会中止整个多批 Run。现在这两类错误分类为可重试（实测 3/4 的饥饿调用在 3 次内恢复，模型每次重掷推理路径），其余错误一律不重试。rig 与 CLI agent 两条路共用同一套分类。

07 / FALLBACK

确定性分组：LLM 之下的第二生产者

生产主拆分器是 LLM；当其计划过不了校验，plan_from_diffs（保守默认、保仓库序）接管并完成 Run。引擎不是死代码——它是 BatchPlanner seam 背后的确定性第二生产者。

1
Adjacency（文件内）
连续 hunk 间隔 ≤ adjacency_gap（默认 3 行）未变行 → 合并为一个 Block；join_same_context 额外合并共享 git 上下文头（函数/节名）的 hunk——最强「同一编辑」信号。
第二阶段
2
Same-scope（跨文件）
不同文件但共享父目录的 Block 合并。默认关闭——同目录只是「同一逻辑变更」的弱代理。根目录文件（Cargo.toml/README）永不自动合并。
v1 的保守主义是显式的

输出必是合法划分（每个 hunk 恰好落一个 Block）→ 直接喂 validate_batch_plan 与 staging。被 adjacency 拆成多 Block 的文件不被 same-scope 经由兄弟文件拉回。每个 Block 携带 BlockHeuristic（Single / Adjacency / SameContext / SameScope），作为批次 reason 浮出给用户。

08 / CONFLICTS

2
逐文件 ResolutionGenerator::resolve_conflict

09 / RENDER

渲染层：无框架的流式终端 UI

ADR 0013 禁 TUI 框架——一切手绘。分工：Markdown 画家管「画什么」，Reasoning feed 管「何时画」，progress 管帧/行字节装配。

◧
Reasoning feed

流式思考的原位滚动窗口：边想边重绘，思考结束整窗擦除——滚动缓冲区不留残迹。无推理 delta（CLI print 模式 / API 冷启动）→ 加载帧 + 宽限期后的解释提示。

▦
Markdown 画家

纯函数：部分 Markdown → ANSI styled rows。行级分类 + 围栏状态、内联 **bold**/`code`、syntect 代码高亮、通用 wrap 引擎。零 IO，全管线可单测。

◐
Palette

所有颜色经由 WCAG 校验的角色函数（success/pending/caution/added/removed…），按 Commit Type 键控——渲染器调角色，绝不手搓 console::Style。

↕
DSR 光标

终端几何探针走真实 PTY 测试；DSR 查询（~200ms 阻塞 tty IO）进 spawn_blocking；探针失败降级到 fallback 窗口——装饰永不弄坏提交。

测试策略

约 330 个测试全在 cargo test 里，两层，零网络、零 API key、完全 hermetic、并行安全。

层 1 · 内联单元测试
  • 每模块 #[cfg(test)] 同目录共存（sibling tests.rs 或尾部 mod 块）
  • 纯逻辑：diff 解析、NDJSON 解码、容错 JSON、配置迁移、分组启发式、校验规则
  • 命名是行为句：commit_batch_loop_aborts_after_partial_commit
  • 桩队列耗尽即 panic——欠编排的测试响亮地失败
层 2 · e2e（src/e2e/）
  • seam 捆绑包驱动 default_run/commit_run/resolve_run
  • 真 git 仓库在每测试独立 tempdir——不 chdir、不全局锁、真 hooks（含 restaging pre-commit 路径）
  • LLM/UI 全部脚本化桩：resolver_returning / prompt_queue / menu_queue
  • 真实 PTY harness 测 DSR 光标；start_paused tokio 时钟只用于 reasoning feed

每次启动跑两次幂等迁移：位置迁移（0012，旧 macOS 路径 → 新路径，新文件已存在则静默跳过）和 preset 迁移（陈旧 CLI preset 的 args 原地重写；只动与已知旧快照字节相同的配置，自定义命令永不碰）。迁移失败只记日志，不阻塞运行。

发布 cargo-dist + GitHub Actions

发布构建走 [profile.dist]（thin LTO + strip）→ target/dist/aic。版本永不在 PR 里 bump——维护者经 prepare-release.sh / release.sh 操作（脚本自带 bash 单测套件）。发布档案用 zipsign 签名，Unix .tar.gz + Windows .zip 两种格式都必须保留压缩 feature（砍掉 compression-tar-gz 会编译掉自更新的 tar 提取臂——Cargo.toml 里那条注释是承重的）。

一句话总结

aic = 纯函数 diff 管线（解析→编号→JSON 信封）+ 不可信 LLM 计划的强校验（精确 hunk 划分，失败降级确定性引擎）+ 两套索引空间的状态机 staging（hook 免疫）+ seam 驱动的全链路可测（真 git tempdir + 脚本化 LLM）。LLM 负责「理解意图」，工程负责「绝不信它」。
